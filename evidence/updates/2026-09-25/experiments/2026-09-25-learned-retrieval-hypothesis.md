# Experiment B candidate: protocolized retrieval of learned relations

**Status: future research hypothesis, not an executed experiment or application
claim.** Recorded from the user's research-synthesis suggestion on 2026-09-25.
Current Experiment A verification and quality work continue separately.

## The application hypothesis

A protocolized, identifier-only component could retrieve useful related products
when the target relation must be inferred from observations or judgments rather
than enumerated from the available graph and its known rules. It must compete
with simple retrieval and ranking methods before we claim that application.

Here "learned" does not mean mathematically non-computable. It means the serving
system lacks a complete rule or factual table that already determines the right
answer for an unseen query. A stored answer should still be tested against lookup.
Hiding TYPE/COLOR labels can test reconstruction, but does not convert their
known SAME rule into evidence of commercial compatibility or user preference.

This makes the existing split explicit:

| Research track | Question | Evidence required |
| --- | --- | --- |
| Experiment A: current TYPE/COLOR SAME | Can the system match a known oracle and serve that quality efficiently? | Oracle parity and matched-quality systems measurements |
| Experiment B: future learned relation | Can PLM predict useful held-out relations better than simpler methods, or serve comparable quality more efficiently? | Independent labels, leakage-resistant evaluation, competitive baselines and measured costs |

A negative result is useful. If a small ranker achieves the same quality more
cheaply, the proposed decoder application has not earned its complexity.

## Candidate relation and data requirements

The leading family is **complementary compatibility**, consistent with the
already deferred COMPLEMENTARY scope. Examples might use independently judged
product pairings or observed successful combinations. These are candidate data
sources, not selected datasets or verified facts about Pokémon.

Co-purchase or co-occurrence can provide an observable prediction target, but
does not by itself prove compatibility: exposure, popularity and substitutes can
also generate those events. If such data are chosen, name the task after the
actual observation and limit the claim accordingly. Missing observations are
unknown unless the labeling process justifies treating them as negatives.

Before execution, select and freeze a dataset, target semantics, provenance,
timestamp availability, judged negatives or implicit-feedback convention,
candidate universe and minimum useful effect. Document whether labels are
complete answer sets, graded judgments or sparse positives. A synthetic latent
relation may serve as an engineering smoke test, but cannot support the real
application claim. Labels generated by a known rule remain rule-distillation
evidence; labels generated by another model remain teacher-agreement evidence
until externally validated.

Preserve genuinely meaningful steering: the dataset must support distinguishing
the requested relation/context rather than allowing a model to ignore it. Do not
invent extra dimensions just to populate tokens. Any future protocol extension
needs a separately versioned contract; this note adds no mode, dimension or token
to v1, and does not revive RELATED.

## Baselines that must have a fair chance

All methods receive the same permitted training observations, identifiers and
candidate universe. If a method receives extra text, attributes or interaction
history, separate that information regime explicitly rather than crediting an
architecture with an information advantage.

| Baseline or ablation | What it tests | Current repository status |
| --- | --- | --- |
| Training-only lookup and dimension-specific popularity | Whether stored answers or popular items suffice | Popularity scorer exists; lookup must be adapted to the new task |
| Simple item-neighborhood retrieval | Whether nearest observed interaction/label profiles suffice | Proposed; fit similarity statistics on training data only |
| Small relation ranker or matrix factorization | Whether low-capacity learned scoring suffices | ComplEx scorer exists; suitability and new-data interface need verification |
| Direct PLM membership head | Whether the auxiliary scorer already supplies the useful signal | Current saved-head ablation exists; must be retrained/evaluated for the new relation |
| PLM protocol generation and any declared set composition | Whether the complete proposed component adds value | Current implementation exists for SAME; new relation support is not implemented |

Existing code leads are `plm.baselines.PopularityScorer`,
`plm.baselines.ComplExScorer` and `plm.evaluation.evaluate_ranking`; they are not
already certified for this future task. ComplEx is a primary literature baseline
for relational link prediction, including asymmetric relations
([Trouillon et al., 2016](https://proceedings.mlr.press/v48/trouillon16.html)).
If the selected target is implicit feedback, a matrix-factorization model with
a ranking objective is another candidate; BPR provides one such objective
([Rendle et al.](https://arxiv.org/abs/1205.2618)). These references motivate
comparisons, not claims that either method will win on our data.

Tune every trainable baseline on validation under disclosed budgets. Compare
both a practical tuned baseline and, where useful, a separately labeled
parameter/compute-matched comparison. A deliberately weak baseline is not useful
evidence for the application.

## Prevent answers from leaking through the split

Freeze the split before deriving graph features, neighborhoods, retrieval indexes
or training records. Preserve the separation through checkpoints and evaluation.
For symmetric pair labels, keep `(a,b)` and `(b,a)` in the same partition; also
group duplicate events and repeated judgments. For temporal data, derive features
only from information available before the prediction cutoff.

Declare one primary generalization task. Held-out pairs among known entities,
held-out query contexts, future events and entirely new products answer different
questions and must be reported separately. An ID-only model has no learned
semantic representation for a genuinely unseen product; adding an unused token
does not solve cold start. Do not claim cold-start capability without a declared
source of usable features or a defined adaptation procedure.

The current symmetric head satisfies z(s,d,t)=z(t,d,s) mathematically. A directional
target may contradict that constraint. Decide target symmetry from its semantics
and evidence before choosing the model; do not silently symmetrize labels to fit
the existing architecture.

## Measurements and a falsifiable claim

For a query q and candidate product i, compare learned scores f(q,i). At a fixed
external output budget K, a ranker returns TopK_i f(q,i). K remains evaluation/
serving metadata, never a numeric protocol token. PLM must be evaluated on its
actual returned identifiers under the same output budget; next-token ranking
alone is not evidence of complete generation quality.

Use ranking metrics such as Recall@K and MAP for appropriate sparse-positive
tasks; add a declared graded-ranking metric if graded labels justify it. Define
the candidate universe, seen-item filtering and negative sampling identically
across methods. Sampled-candidate and full-catalog results are different tests.
Existing MRR/Hits/MAP code is a starting point; any missing metric needs its own
implementation and tests before the run.

Use set precision/recall/F1 and exact-set accuracy only where label completeness
supports those interpretations. Do not call an unobserved but plausible returned
product a proven error merely because an implicit-feedback dataset is sparse.
Measure protocol validity, uniqueness, termination, fallback and abstention
separately from relevance quality.

Predeclare the primary metric, meaningful effect size, repeated seeds and
uncertainty analysis before observing results. Seeds on the same queries are
not independent test datasets; paired query-level comparisons should respect
the unit of dependence in the data. Reserve a protected final split and access
it only after model/baseline selection is frozen.

Evaluate end-to-end p50/p95 latency, throughput under concurrency, memory and
energy at matched quality. Include index construction, training and update costs
where relevant. A faster system with materially worse relevance does not prove
the proposed application. A stronger application claim requires either a useful
quality gain at an acceptable measured cost or comparable quality with a useful
measured systems advantage over the strongest tested simple baseline.
